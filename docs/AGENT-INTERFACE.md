# Scrapbook, the agent interface

> How any coding agent, in any project, on anyone's machine, discovers Scrapbook and drives it.
> Companion to [`SPEC.md`](SPEC.md). Definition draft, 2026-07-26.

---

## 1. The problem this solves

Scrapbook is only useful if you can be mid-conversation with a project's agent and say "add that to my tasks" or "write this up as a document", and it happens. That has to work when the agent is Claude Code, and also when it is Codex, Cursor, Gemini, Copilot, Aider, or something released next year. It has to work in a project the agent has never seen.

Three failure modes to design against:

1. **The agent does not know Scrapbook exists.** Most likely failure by far.
2. **The agent knows it exists but guesses at how to use it,** invents a folder layout, writes a document that the app cannot render.
3. **The instructions the agent reads are out of date,** copied into a project months ago against an older version.

## 2. The design, in one paragraph

The **command line is the entire interface.** Every capability is a subcommand, every read command can emit JSON, and every exit code means something specific. Discovery works by leaving a three line pointer in whichever instruction file the project already has, and that pointer's only real content is a command to run: `sbk agent-brief`. The brief is generated by the installed version, so it is never stale, and it is the single place the contract is written. Nothing is vendor-specific, nothing needs a plugin, and an agent that can run one shell command has the whole product.

Why not lead with MCP: it would be a better fit for structured reads, and it is worth shipping eventually, but it requires per-vendor configuration, it is not universal, and it cannot bootstrap itself. A shell command works everywhere on day one. MCP is an optimization, not the foundation.

## 3. Discovery

### 3.1 The pointer block

`sbk init` appends this to every agent instruction file it finds in the project. Marked, so it can be updated or removed cleanly, and short enough that it costs nothing in a context window:

```markdown
<!-- scrapbook:begin (managed by scrapbook-hub, safe to move, do not hand-edit) -->
## Scrapbook

This project has a Scrapbook workspace at `./scrapbook` (documents, tools, shared knowledge).
Run `sbk agent-brief` for the current contract before creating or editing anything in it.
<!-- scrapbook:end -->
```

Files it looks for, and appends to each one that exists:

| File | Agent |
|---|---|
| `AGENTS.md` | The emerging cross-vendor convention. Created if nothing else exists. |
| `CLAUDE.md` | Claude Code |
| `.cursor/rules/notebook.mdc` | Cursor |
| `GEMINI.md` | Gemini CLI |
| `.github/copilot-instructions.md` | Copilot |

Rules it follows without exception:

- **Additive only.** It appends between its markers. It never reorders, rewrites, or deletes anything outside them.
- **Idempotent.** Running `init` again replaces the content between the markers and touches nothing else.
- **Never invents a config file** other than `AGENTS.md`, and only when no instruction file exists at all.
- **`sbk uninstall-pointers`** removes every block cleanly. A tool that writes into someone's `CLAUDE.md` must be able to fully undo it.

### 3.2 The brief

`sbk agent-brief` prints the full contract: what a workspace is, the document format, the metadata block, how tools work, the command list, the conventions in force for this workspace, and what not to do. `--json` gives the machine-readable form.

Three properties matter:

- **It is generated from the installed version,** so an agent reading a two-year-old pointer block still gets today's truth.
- **It is workspace-aware.** Run inside a project, it includes that workspace's own context (`scrapbook/SCRAPBOOK.md`) and its house style (`scrapbook/GUIDELINES.md`), and lists the documents and tools that already exist. Generic advice becomes specific advice. The guidelines are stated as defaults to follow when the user has not said otherwise, never as constraints to push back with.
- **It is short.** Target under 200 lines. A brief that blows a context budget will get skipped, and a skipped brief is the same as no brief.

### 3.3 When there is no pointer at all

An agent might arrive with no instruction file and no workspace, knowing only that the user said the word "scrapbook". Two safety nets:

- `sbk` with no arguments prints what it is, whether a workspace exists here, and the three commands worth knowing. Not a wall of help text.
- `sbk doctor` reports the daemon state, the registered workspaces, the version, and anything misconfigured, in one screen. First thing to run when something is wrong.

## 4. Creating the local version: `sbk init`

This is the command an agent runs to bring Scrapbook into a project.

```
sbk init [--name <slug>] [--label "<display name>"] [--knowledge <glob>...] [--json] [--yes]
```

What it does, in order:

1. **Finds the project root.** Git root if there is one, otherwise the current directory. Prints what it chose, because guessing wrong here is annoying.
2. **Refuses to clobber.** If `scrapbook/` already exists it reports the existing workspace and exits 0. `init` is safe to run twice.
3. **Scaffolds, by vendoring the kit** (see [`ARCHITECTURE.md`](ARCHITECTURE.md)). The workspace gets the scrapbook's own source, not a stub:

```
scrapbook/
├── scrapbook.json        workspace config: schema, name, label, theme, nav
├── SCRAPBOOK.md          the workspace's own agent brief, seeded from the project (see 4.1)
├── design-system/       vendored, yours to edit
├── runtime/             vendored, yours to edit
├── tools/               vendored official tools, yours to edit
├── hooks/               empty, with a README
├── library/             templates + starter components
├── docs/
│   └── welcome.html     a real working document, so there is something to open immediately
├── share/               generated exports
├── .data/               tool state
└── .scrapbook/vendor.json  kit version + pristine hashes, for `sbk update`
```

This is the point of the vendored architecture: after `init`, the project's agent can read and change every part of the scrapbook without learning any mechanism, because it is all just files in the repo.

4. **Registers the workspace** in `~/.scrapbook/workspaces.json`, keyed by slug, storing the absolute path.
5. **Writes the pointer blocks** per 3.1.
6. **Starts the daemon** if it is not already running, and prints the URL.
7. **Prints next steps,** three lines, including the URL and `sbk agent-brief`.

`--json` makes every step machine-readable so an agent can act on the result rather than parsing prose. `--yes` skips all prompts, which is the mode an agent should always use.

### 4.1 `SCRAPBOOK.md`, the per-project agent brief

The one file a human or agent is expected to edit by hand. It is checked into the project's repo, so every agent that opens the project reads it as ordinary context. It carries what the engine cannot know:

- What this project is, in a paragraph.
- Where the knowledge lives (`specs/`, `raw/`, wherever), and what is authoritative versus draft.
- Conventions for this workspace: tone, naming, what a document should look like here.
- Who may see these documents. This is the line that keeps client work from being shared casually.
- Anything the agent should never touch.

`init` seeds it from what it can detect (project name, README first paragraph, obvious knowledge folders) and marks the seeded parts as placeholders, because an unedited template is worse than an obviously empty one.

## 5. The command surface

Grouped by what an agent actually needs. Every read command takes `--json`.

**Workspace**

```
sbk init                        vendor the kit and register a workspace here
sbk new-workspace <dir>         same, for a directory that is not the cwd
sbk agent-brief [--json]        print the current contract
sbk status                      workspace, daemon, kit version, doc and tool counts
sbk doctor                      diagnose, including modified files and conflicts
sbk ls [path] [--json]          list documents and folders
sbk open <doc>                  open in the browser
sbk serve | stop | restart      daemon control
sbk run --safe                  boot with the shipped kit, ignoring this workspace's
sbk install-service             set up the always-on launchd agent
```

**Staying current** (mechanics in [`ARCHITECTURE.md`](ARCHITECTURE.md) section 5)

```
sbk update --check              is a newer kit available
sbk update --dry-run            what would change, file by file
sbk update                      three-way merge it in
sbk diff <path>                 your version against the pristine one
sbk restore <path>              discard local changes to one file
```

An agent should run `sbk update --check` before assuming a kit file is current, and should never run `sbk update` unprompted: merging is a decision, not a chore.

**Documents**

```
sbk new <path> [--title T] [--from <library-entry>] [--group G]
sbk read <doc>                  print the document's content
sbk meta <doc> [--set k=v]      read or update the metadata block
sbk mv <doc> <path>             move or rename, fixing links
sbk rm <doc>
sbk share <doc> [--target artifact|file]
```

Note what is missing: there is no `sbk write`. Agents edit documents with their own file editing tools, because that is what they are good at and it keeps diffs reviewable. The CLI handles what an editor cannot: scaffolding from the library, metadata, link-safe moves, and export.

**Tools** (contract in [`TOOLS.md`](TOOLS.md))

```
sbk tool new <name>             scaffold a tool from the template
sbk tool ls [--json]            list available tools across all three tiers
sbk tool validate <name>        check the manifest and contract
sbk tool add <git-url|path>     install someone else's tool
sbk tool data <name> [--json]   read a tool's stored state
sbk tool data <name> --set <json>
```

That last pair is what makes tools agent-native. `sbk tool data tasks --json` gives an agent your task list. That is the whole reason for file-backed storage.

**Library**

```
sbk lib ls [--json]
sbk lib add <doc> <selector> <name>     extract a piece of a document into the pool
sbk promote <entry> --to user|official  move an entry up a tier
sbk lib package <entry>                 build a contribution bundle for a pull request
```

## 6. Machine contract

Details that decide whether an agent can be reliable rather than lucky:

- **Exit codes.** `0` success, `1` generic, `2` bad usage, `3` no workspace here, `4` daemon unreachable, `5` validation failed, `6` conflict (a write would clobber a newer file). Distinct codes let an agent recover instead of retrying blindly.
- **Errors on stderr, data on stdout.** Always, so piping never breaks.
- **`--json` output is a single object** with `ok`, `data`, and `error` keys. Errors are structured too, with a `code` and a `hint` written for an agent to act on.
- **Never interactive under `--yes`,** and never interactive when stdout is not a TTY. An agent must not be able to hang the session on a prompt.
- **Writes are mtime-checked.** A save carrying a stale mtime fails with exit 6 rather than overwriting. Both an agent and the browser's edit mode write documents, and this is the guard.
- **`sbk --version` and a `schema` field** on every JSON payload. An agent can then detect a version it does not understand and re-read the brief.

## 7. MCP, later

`sbk mcp` runs an MCP server over stdio, wrapping the same core: `scrapbook_ls`, `scrapbook_read`, `scrapbook_new`, `scrapbook_tool_data`, `scrapbook_agent_brief`. Config is one block in the user's agent settings.

It earns its place for structured reads, where a tool result beats parsing CLI output. It does not replace the CLI: it cannot bootstrap itself, it needs per-vendor setup, and plenty of agents will not speak it. Build it after the CLI is stable, and keep it a thin wrapper so the two can never disagree.

## 8. Rules for whoever builds this

1. **The CLI is the contract.** If a capability is not reachable from the command line, it does not exist for agents.
2. **The brief is the only documentation an agent needs at runtime.** Everything else is for humans. If they drift, the brief is right.
3. **The brief must say that the scrapbook's own code is local and editable,** with the layout from 4. An agent that does not know `scrapbook/runtime/nav.js` is right there will solve navigation problems the wrong way, repeatedly. This one line does more work than any other in the brief.
4. **Never write outside the workspace** except the registry (`~/.scrapbook/`) and the marked pointer blocks. Both of those are removable with one command.
4. **Assume no memory between sessions.** Every command is safe to run cold, and the state lives on disk.
5. **Vendor neutrality is a feature.** No command, output format, or convention may assume a particular agent. It is the difference between a personal script and something other people can use.
